# Emergency QR frontend implementation plan

**Goal:** Implement only Miki's frontend from emergency-qr-v1, for web and Expo Go.
**Architecture:** Expo Router and shared React Native components; all HTTP in api.ts; platform-specific key storage; no backend or production mocks.
**Tech stack:** create-expo-app default template, Expo 57, React Native, TypeScript, QR SVG, SecureStore.
**Spec:** User supplied emergency-qr-v1 common contract and frontend section. Frontend-only clarified on 2026-10-01.

## Global constraints
- Six screens, exact API contract, Russian copy, #F5F8FB / #142235 / #087F8C theme.
- Native key in SecureStore; browser memory only; QR encodes server publicUrl only.
- No fake successful requests or persistent public data cache; no backend/database deliverable.
- Device and server integration verification reported separately from web build.

## Tasks
- [x] Compatible Expo Router scaffold; remove tutorial screens; single-page export.
- [x] Typed API client/session; tests for authorization isolation, errors, timeout, 204, logout, 401, storage failure.
- [x] Shared layout, buttons, inputs, confirmations and public-card preview.
- [x] Six routes wired to actual API operations, with loading/error/retry states.
- [x] Typecheck, tests, expo-doctor, lint, web export; wide/narrow browser verification.
- [x] README and checks report; frontend.zip containing only frontend/ source/config/docs/lockfile.

## Review focus
- Stale owner requests after logout/account change cannot restore data or clear a newer session.
- Public route changes, refresh, background and 404 remove stale data.
- Storage failure after creation still permits manually saving the key.
- API misconfiguration shows an actionable error without crashing the landing screen.
- Double-submit protection and destructive confirmations work on web/native.

Supplied specification fixes architecture and authorizes implementation. API/session delegated, UI/integration local; no external publication.
