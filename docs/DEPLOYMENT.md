# Постоянный адрес Emergency QR с HTTPS

Эта конфигурация запускает сайт и API на одном постоянном домене, например
`https://qr.example.com`. Сервер должен работать постоянно и иметь доступ к
интернету: выключение компьютера с локальным демо делает его QR недоступным.
Постоянный домен сохраняет адрес QR при обновлении приложения. Доступность
зависит от работы сервера, DNS и продления домена; абсолютная доступность не
гарантируется.

## Что требуется

- Linux-сервер с Docker Engine и Docker Compose, постоянным диском и публичным IP.
- Собственный домен или поддомен. Его A-запись указывает на IPv4 сервера;
  AAAA-запись нужна только при действительно настроенном IPv6.
- Входящие TCP 80 и 443 разрешены на сервере и у провайдера. UDP 443 необязателен
  для HTTP/3. Порт 3001 наружу не публикуется.

Caddy получает и обновляет публичный TLS-сертификат автоматически при верных DNS
и доступных портах; HTTP перенаправляется на HTTPS. Для сертификатов выделен
постоянный том. См. [требования Caddy](https://caddyserver.com/docs/automatic-https).

## Первый запуск на сервере

Команды ниже выполняются в корне проекта на Linux-сервере. Они не требуют
Node.js на хосте: образ использует Node.js 24 и настоящие lock-файлы всех трёх
пакетов. Не переносите в исходный архив `.env`, локальные SQLite или приватные
ключи владельцев.

```sh
cp deployment/.env.example deployment/.env
```

Укажите свой домен в `deployment/.env`, например `DOMAIN=qr.your-domain.tld`.
Протокол, путь и завершающий слеш в этой переменной не нужны. Затем:

```sh
docker compose --env-file deployment/.env -f deployment/compose.yaml config --quiet
docker compose --env-file deployment/.env -f deployment/compose.yaml up -d --build
docker compose --env-file deployment/.env -f deployment/compose.yaml ps
curl --fail https://qr.your-domain.tld/api/v1/health
```

Health должен вернуть `{"ok":true,"contractVersion":"emergency-qr-v1"}`.
Проверьте сайт и QR второго телефона через мобильный интернет, затем создание,
изменение, отключение и замену QR только на вымышленных данных.

`DOMAIN` одновременно задаёт build argument `PUBLIC_WEB_ORIGIN`, встраиваемый
`EXPO_PUBLIC_API_URL=https://DOMAIN/api/v1` и runtime `PUBLIC_WEB_ORIGIN`.
При изменении домена повторите `up -d --build`: одного перезапуска недостаточно,
поскольку Expo встраивает API URL в JavaScript при сборке. Локальные `.env`
исключены из Docker build context через `Dockerfile.dockerignore`.

## Хранение и обновления

SQLite хранится в именованном томе `emergency-qr_card_data`, сертификаты —
`emergency-qr_caddy_data`. Приложение работает пользователем `node`, новый том
получает соответствующие права при первом создании. Перезапуск контейнера и
пересборка образа сохраняют карточки. Не запускайте `docker compose down -v`:
этот флаг удаляет постоянные тома.

После загрузки новой версии проекта используйте ту же команду `up -d --build`.
Политика `unless-stopped` возвращает процессы после сбоя или перезапуска Docker;
Docker должен автоматически запускаться вместе с сервером. Healthcheck отмечает
доступность API; сам по себе статус unhealthy не перезапускает зависший процесс.
Для наблюдения достаточно внешней проверки `/api/v1/health` без карточек и токенов.

Тома переживают удаление контейнеров, но не потерю диска сервера. См.
[поведение Docker volumes](https://docs.docker.com/engine/storage/volumes/).

Минимальный согласованный backup с короткой остановкой приложения:

```sh
mkdir -p backups
docker compose --env-file deployment/.env -f deployment/compose.yaml stop app
docker compose --env-file deployment/.env -f deployment/compose.yaml cp app:/app/data ./backups/card-data-YYYY-MM-DD
docker compose --env-file deployment/.env -f deployment/compose.yaml start app
```

Копируется весь каталог, включая возможные WAL/SHM. Если копирование завершилось
ошибкой, всё равно запустите приложение последней командой. Храните зашифрованную
копию отдельно от сервера и проверяйте восстановление в отдельной среде.
Не копируйте только основной SQLite-файл из работающего процесса.

## Proxy, лимиты и приватность

Caddy имеет фиксированный адрес `172.30.42.2` в отдельной внутренней сети.
Backend доверяет `X-Forwarded-For` только от этого адреса через `TRUST_PROXY`;
Caddy заменяет клиентское значение реальным адресом соединения. Поэтому лимиты
применяются отдельно к посетителям, а прямой клиент не может подменить свой IP.
По умолчанию вне этой конфигурации доверие proxy выключено. `true`, hop counts,
имена хостов и CIDR `/0` запрещены. При конфликте Docker-подсети измените её,
фиксированный адрес Caddy и `TRUST_PROXY` согласованно.

CORS разрешает только собственный HTTPS origin; native-запросы без Origin
сохраняют обычную Bearer-авторизацию. API и карточки используют `no-store`.
Access-логи Caddy не включены; исключён также HTTP error logger, который может
содержать URI. Не включайте debug/trace и сторонние access-логи с путями
`/q/<token>`, телами, Authorization или данными контакта. Обычные сообщения
запуска и выдачи сертификата сохраняются.
Настройки logger описаны в [документации Caddy](https://caddyserver.com/docs/caddyfile/options#log).

SQLite в контейнере начинается с пустой базы. Если нужны локальные тестовые
карточки, перенос базы выполняется отдельно после её остановки с восстановлением
владельца тома `node` (UID 1000). Уже напечатанный локальный QR не превращается
в публичный: получите QR с новым доменом в кабинете владельца и сохраните его
заново. Для native Expo настройте публичный API URL и перезапустите Expo.

## Что проверено при подготовке

Docker CLI и Compose установлены; конфигурация проверена командой `compose config`.
Docker Engine в локальной среде не запущен, поэтому сборка образа, запуск Caddy,
выдача сертификата и публичный домен ещё не проверены. Никакой хостинг или
платный ресурс этой подготовкой не создан; публичное размещение не выполнено.

Backend-тесты отдельно проверяют доверенный proxy, разные клиентские лимиты,
игнорирование поддельного заголовка от недоверенного соединения и отклонение
опасных настроек. Фактические результаты — в `backend/CHECKS_BACKEND.md`.
