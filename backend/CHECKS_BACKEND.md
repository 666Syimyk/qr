Проверена объединённая структура с настоящим `database/src/index.ts`.

## Проверено

- Восемь маршрутов `emergency-qr-v1`, точные ответы и HTTP-коды, UUID,
  независимые 43-символьные токены и хранение SHA-256 ключа владельца.
- Авторизация каждого действия владельца; чужой, отсутствующий и публичный
  токен не дают права управления. Ключ и hash отсутствуют в GET-ответах.
- Строгие обязательные и вложенные поля, длины, телефон, согласие,
  malformed JSON, 16 КБ, Content-Type, JSON-ошибки 400/401/404/413/415/429/500.
- Публичный список полей, скрытая заметка `null`, одинаковые 404 для
  неизвестной, выключенной, удалённой карточки и старого QR.
- CORS allowlist, preflight, native без Origin; раздельные лимиты с
  Retry-After, недоверие X-Forwarded-For, отсутствие stack trace и no-store.
- Public URL зависит от конфигурации, а не Host/X-Forwarded-Host.
- `.env` и относительные пути разрешаются от backend независимо от cwd;
  CLI configure проверяется отдельными процессами в временном каталоге.
- SPA fallback, настоящие 404 ресурсов/API, 503 до появления сборки,
  защитные заголовки и запрет служебных и скрытых файлов.

Дополнительно выполнены реальные HTTP-запросы с пустым JSON-телом,
JSON-примитивом, неподдерживаемой кодировкой и сжатым телом: получены
ожидаемые JSON-ошибки 400 и 415.

## Настоящая SQLite-интеграция

Тест `tests/integration.test.ts` использует `openRepository` модуля database
и отдельный временный SQLite-файл. Подтверждён цикл:

создание → публичное/приватное чтение → закрытие и повторное открытие базы →
изменение → выключение → включение → замена QR в выключенном состоянии →
повторное открытие → включение текущего QR → удаление → повторное открытие.

Проверены сохранность ID, данных, статуса и нового токена, недоступность
старого QR, скрытие заметки и невозможность управления после удаления.
Это настоящая интеграция Express и SQLite; fake используется только API-тестами.

## Исправление при объединении

В статической раздаче воспроизведён обход: junction внутри `dist` с публичным
именем мог указывать на защищённый каталог `dist/database` или скрытый каталог.
Проверялось нахождение цели внутри dist, но не защищённые сегменты реального
пути. Теперь и обычные файлы, и SPA index проходят обе проверки после
`realpathSync`. Регрессионный HTTP-тест сначала падал с 200 вместо 404,
после исправления проходит; проверены обе разновидности alias.

При проверке настоящей web-сборки выявлена ошибка SPA 500, если настроенный
каталог экспорта имеет скрытого предка, например `.integration/web`.
Express `sendFile` проверял скрытые сегменты всего абсолютного пути.
Теперь fallback передаёт `index.html` относительно явно заданного `root: dist`,
сохраняя предварительную проверку фактической цели. Регрессионный тест сначала
воспроизвёл 500, после исправления проверил `/`, `/create`, `/q/<token>` и
JS-ресурс с 200, а `.env` с 404. Полный API suite и typecheck повторно прошли.

Для постоянного размещения добавлен необязательный `TRUST_PROXY`: только
явные IP/CIDR, без доверия по умолчанию, `true`, hop counts и `/0`.
Два новых теста сначала воспроизвели общий лимит и отсутствие валидации,
после реализации подтвердили отдельные лимиты за доверенным proxy,
игнорирование поддельного X-Forwarded-For от недоверенного соединения
и отказ опасным настройкам. Повторно прошли полный API suite, typecheck
и настоящая SQLite-интеграция.

## Ограничения этого отчёта

- Один тест **SKIP**: Windows-учётной записи недоступно создание файловой
  символической ссылки (`EPERM`). Проверки directory junction выполнены.
- Web host здесь проверен HTTP-тестами с HTML-фикстурой. Проверки настоящей
  Expo-сборки, браузера, запуска общего сервера и упаковки относятся к общему
  отчёту проекта, а не к этим backend-тестам.
- Native в Expo Go, сканирование вторым физическим телефоном и внешнее HTTPS
  этими тестами не подтверждаются.

Использованы только вымышленные данные. Готовность к медицинской эксплуатации
не заявляется.
